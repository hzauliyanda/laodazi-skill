# 历史文章生成 + 豆包史实校验闭环 + 润色

一条龙：生成初稿 → 豆包校验 → 裁决 → 修订 → 再校验 → …… → 定稿（史实闭环收敛）→ 润色 → 终稿。中间产物全部落盘。

> 顺序硬约束：**先把史实校验闭环跑到收敛（⑤定稿），再润色（⑥）**。不要一边润色一边校验——润色只在史实已定稿之后做一次，且不得改动已核验的史实与史料引文。

## 快速使用

```bash
/laodazi-verified-writer "杀于谦、抄张居正、灭戚家军！这三起血案是怎么把大明逼上绝路的"
```

可选参数（跟在主题后面，空格分隔）：

| 参数 | 说明 |
|------|------|
| `manual` | 跳过浏览器自动化，直接走半自动兜底（用户手动贴豆包） |
| `rounds=N` | 最大校验轮数，默认 5 |
| 切法参数 | 可透传 `opening_style` / `ending_style` / `topic_type` / `thread_device` 给生成 API（可选值见 laodazi-writer 的切法池表），不传则单篇随机、批量排班 |

（旧版的 `quick` 参数已废弃，API 不再支持 quick 模式。）

## 模型分工（硬约束）

- **执行型步骤（①生成、②豆包校验、④修订）**：用 Agent 工具起子代理执行，`model: opus`（opus-4.8）。
- **判断型步骤（③裁决、⑤定稿终审、⑥润色）**：留在主会话执行，不下放子代理。⑥润色是写作质量任务，在主会话调用 `laodazi-history-polish` skill，不下放 opus 执行子代理。

子代理之间通过磁盘文件交接（文章文件、校验报告文件），不在返回值里传全文。

## 目录与落盘规范

写入前必须先读取并遵守 `/Users/liyanda/Documents/SynologyDrive/.FILE-RULES.md`。

```
/Users/liyanda/Documents/SynologyDrive/01-自媒体/内容创作/待润色/
├── <主题>.md              # 当前最新版（每轮修订就地覆盖，定稿即此文件）
└── <主题>-过程稿/          # 中间产物
    ├── v1.md, v2.md ...           # 每一版快照（生成/修订完成后立即复制一份）；最后一版 vN = 校验定稿（未润色）
    ├── 豆包校验-第1轮.md ...       # 每轮豆包原始回复全文
    ├── 校验记录.md                 # 汇总记录（见⑤）
    └── 润色前-校验定稿.md          # ⑥润色前，把校验定稿另存一份留底（见⑥）
```

- 主题作为文件名：**直接用用户给的完整主题原文，不要简写、概括或另起标题**（哪怕主题很长、像一句话）。只去掉文件系统非法字符——半角 `/ : * ? " < > |` 和换行；中文全角标点（`，`、`：`、`""` 等）一律保留，不要删、不要转成别的。文章文件名与其 `-过程稿/` 目录名必须用同一个完整主题串，保持一致。
- 每个文件写入后 `chmod 777`；新建过程稿目录后 `chmod -R 777`。

## 流程

### ① 生成初稿（opus 子代理）

**先定切法参数**（主会话在起子代理前决定，规则与 laodazi-writer 一致）：

- **单篇**：4 个切法参数都不传，服务端随机抽取。
- **同一会话/同一天批量多篇**（豆包专家额度内批量跑时常见）：显式传 `opening_style`、`ending_style`、`thread_device` 排班轮换——列出本批已用组合，每篇选未用过的开头和结尾。`topic_type` 按选题指定或留空自判。
- 用户在参数里点名了切法就用用户的。

起 opus 子代理，调文章生成 API（与 laodazi-writer 相同）：

```bash
curl -s --location 'https://article-generator-896616019958.asia-east1.run.app' \
--header 'Content-Type: application/json' \
--data '{"topic": "<主题>", "mode": "full"}'
```

- full 模式 3 步串行（研究→立论+大纲→正文）可能需要几分钟，子代理需设置足够的 timeout（≥300s）并耐心等待。
- 解析返回 JSON 的 `article` 字段，写入 `待润色/<主题>.md`，同时复制一份到 `过程稿/v1.md`。
- 解析 `styles` 字段（本篇实际切法组合），记入校验记录并随摘要返回。**响应里没有 `styles` 字段说明服务端还是旧版**（未部署 2026-07-05 后的代码），不阻断流程，但在最终汇报中提醒用户执行部署。
- 如 `metrics.passed` 为 false，把违禁词/字数问题记入校验记录，但不阻断流程。
- 子代理返回：字数、耗时、文件路径、styles 组合、metrics 摘要（不返回全文）。

### ② 豆包史实校验（CDP 脚本驱动，opus 子代理）

用 `scripts/` 下的 CDP 脚本驱动网页版豆包（**不依赖 chrome-devtools MCP**，本机通常没有；脚本复用 `laodazi-post-to-baijiahao/scripts/shared/cdp.ts`，用 `bun` 运行）。详细定位策略与坑见 [references/doubao-browser.md](references/doubao-browser.md) 实测记录。三条硬规则：

- **【专家模式】**：豆包必须切到"专家模式"再校验，不能用默认"快速"（快速模式实测既漏真错、又误报假错）。
- **【同一个会话】**：整篇文章的多轮复检都在**同一个豆包会话**里进行，round≥2 直接把修订版贴进原会话，**不新开对话**。
- **最多 5 轮**（`rounds=N` 可覆盖）。

**首轮准备（一次性）**：
1. 探测+登录：`bun scripts/doubao-probe.ts` 弹出独立 profile 的 Chrome（`~/.local/share/doubao-verify-profile`，与用户日常 Chrome 隔离，登录态存磁盘、登一次永久复用）。提示用户在弹出窗口登录豆包。
2. 切专家模式：`bun scripts/doubao-set-expert.ts <port>`（port 从 `ps aux | grep doubao-verify-profile | grep -oE 'remote-debugging-port=[0-9]+'` 取）。

**每轮校验**：
1. 把"校验指令 + 当前版本文章全文"合并成一个输入文件。**首轮**用下方固定指令开头；**round≥2** 用固定指纹开头"这是根据你上面意见修订后的版本…请再检查一遍"（脚本靠此指纹排除用户自己的消息）。
2. 发送前确认仍是专家模式（可能被误点回快速）：`doubao-set-expert.ts`（幂等）。
3. `bun scripts/doubao-verify.ts <port> <输入文件> <过程稿/豆包校验-第N轮.md>`。脚本自动：附着现有 Chrome→（round≥2 不加 `--new`，同会话）→抓 baseline→fill+Enter 发送→轮询直到回复稳定→按 baseline-delta 抽取**新回复**落盘。
4. **专家模式思考久（~200–450s），脚本 `MAX_MS` 已设 8 分钟**；若仍被截断，用 `--read-only`（复用持久化的 `.baseline.json`）重抓，或 `doubao-grab-last.ts <port> <out>` 兜底。
5. 读回落盘的报告交主会话裁决（③）。校验报告不长，可直接读文件。

**固定校验指令**（首轮用，写死不要即兴改写）：

```
我接下来发你一段历史文章文本，帮我检查一下史实是否正确。注意：不要引用自媒体文章作为依据，要以权威史料、古书、正史（如二十四史、《资治通鉴》等）和严肃学术著作为准。

请按下面的格式逐条输出检查结果，分两类：

【史实错误】（人物、时间、地点、官职、数字、事件经过或因果与史料明确不符的）
- 错误点：<文章原文表述>
  正确史实：<应为什么>
  史料依据：<具体书名+篇目/卷次>

【文学化演绎】（合理的细节想象、氛围描写、心理刻画、表述略有出入但不违背史实主干的，这类不算错误，仅列出提示即可）
- <简要说明>

如果全文没有史实错误，请明确回复"未发现史实错误"。

文章如下：
```

**降级规则**：脚本连续 2 次失败（登录态失效、页面结构对不上、超时抓不到回复），或用户指定 `manual`，切半自动兜底：

- 用 `pbcopy` 把"校验指令 + 当前版本文章全文"放进剪贴板（`cat 指令文件 文章文件 | pbcopy`）。
- 提示用户："已复制到剪贴板，请在豆包【专家模式】粘贴，然后把完整回复贴回来。"
- 等用户贴回后，把回复存入 `过程稿/豆包校验-第N轮.md`，继续走③。流程不中断。

### ③ 裁决（主会话执行，不下放）

把豆包报告逐条分类，这是防翻车的关键环节：

| 分类 | 判定标准 | 处置 |
|------|----------|------|
| **硬伤** | 在【史实错误】栏、且豆包给出了具体史料依据（书名+篇目），且与自己的历史知识不冲突 | 进入④修订 |
| **存疑** | 豆包列为错误但没给出处，或它给的"正确史实"本身可疑（与常识性史实明显冲突） | 不修，记入校验记录并在最终汇报中告知用户 |
| **演绎** | 豆包列在【文学化演绎】栏，或实质上属于合理创作、细节表述偏差 | 保留不修，记入校验记录 |

**收敛规则**（必须执行，否则循环不会终止）：

- 维护一份"已裁定保留清单"（演绎+存疑）。后续轮次豆包再提相同或实质相同的条目，直接忽略，不计入硬伤。
- 裁决结果：硬伤数 = 0 → 跳到⑤定稿；硬伤数 > 0 且未达最大轮数 → 走④。
- 达到最大轮数（默认 5）仍有硬伤 → 停止循环，进⑤，但在汇报中明确列出未解决的硬伤，交用户人工决定。
- **提前收敛信号**（即使未达 5 轮也应停）：①连续 2 轮报告实质相同 → 剩余项已是固定误判；②豆包**跨轮自相矛盾**（同一条前轮判对、后轮判错，如引文某数字/用字口径反复）；③钻进古籍**逐字校勘的 edition 变体层**、且争议处本是**白话转述**而非逐字引文——这类继续循环只会在变体里打转、永不收敛，甚至越改越生僻，应停并向用户说明。

主会话自己要复核豆包的判断，不盲信：豆包也会记错史实、且跨轮不一致。拿不准的宁可归入"存疑"报给用户，不要改。

### ④ 修订（opus 子代理）

起 opus 子代理，把③裁定的**硬伤清单**（只传硬伤，演绎/存疑一条都不带）拼成 feedback，调 revise API：

```bash
curl -s --location 'https://article-generator-896616019958.asia-east1.run.app' \
--header 'Content-Type: application/json' \
--data '{"topic": "<主题>", "mode": "revise", "article": "<当前全文>", "feedback": "<硬伤清单>"}'
```

- feedback 格式：逐条"原文表述 → 应改为（依据：史料出处）"，多条合并成一个字符串。
- **JSON 转义必须用 python3 或 jq 构造请求体**（文章含换行和引号），禁止 shell 手动拼接。参考：

```bash
python3 - <<'PY'
import json, pathlib, subprocess
article = pathlib.Path("<文章路径>").read_text(encoding="utf-8")
feedback = pathlib.Path("<硬伤清单路径>").read_text(encoding="utf-8")
body = json.dumps({"topic": "<主题>", "mode": "revise", "article": article, "feedback": feedback}, ensure_ascii=False)
r = subprocess.run(["curl", "-s", "--location", "https://article-generator-896616019958.asia-east1.run.app",
                    "--header", "Content-Type: application/json", "--data", body],
                   capture_output=True, text=True, timeout=300)
print(r.stdout)
PY
```

- 取返回 JSON 的 `article` 字段，**覆盖** `待润色/<主题>.md`，并复制快照到 `过程稿/v(N+1).md`，chmod 777。
- revise 模式会保持原文的开头切法、结尾收法和贯穿线索不变，只修正硬伤，不用重新传切法参数。
- 修订完成后回到②，进入下一轮校验。

### ⑤ 校验定稿（主会话）

史实校验闭环收敛（硬伤=0 或达最大轮数）后：

1. `待润色/<主题>.md` 此刻即"校验定稿"（史实已核验，但尚未润色）。
2. 写 `过程稿/校验记录.md`，内容：
   - 本篇切法组合（styles：开头/结尾/贯穿/题型；旧版服务端无此字段则注明）
   - 每轮：豆包报了几条、裁决为硬伤/演绎/存疑各几条、修了什么
   - 已裁定保留清单（演绎+存疑，含理由）
   - 若有未解决硬伤：逐条列出
   - metrics 异常（如有）
3. **不在此处向用户做最终汇报**——先走⑥润色，收尾汇报放在⑥。

### ⑥ 润色（主会话，调 laodazi-history-polish）

史实校验定稿后，对同一个文件做一次老达子风格润色。**这是流程的最后一步，只做一次，不再回到②校验。**

1. **留底**：把当前校验定稿 `待润色/<主题>.md` 复制一份到 `过程稿/润色前-校验定稿.md`，chmod 777。这样润色若走偏，随时能拿回未润色的校验定稿。
2. **调润色 skill**：在主会话用 Skill 工具调用 `laodazi-history-polish`，参数为校验定稿文件的绝对路径。润色 skill 会就地覆盖 `待润色/<主题>.md`（遵守其自身的落盘惯例：只覆盖原文件、不追加 MOVE 日志、不提示移动）。
3. **润色红线（务必在调用前向润色环节明确，防止把已核验的史实改错）**：
   - **不得改动已核验的史实、人名、时间、官职、数字、因果**；
   - **不得改写、删除或新增任何史料引文**（如"（引用自《隋书》卷四十九《牛弘传》：……）"这类），文言锚点原样保留；
   - 只在**文风层面**打磨：口语化、节奏、去 AI 味、标点、前言/结尾等，遵循老达子润色的既有规则（结构保留、缺失前言/老达子说才补、结尾≤3 段、禁编号式框架、禁现代类比等）。
   - 若润色 skill 有"史实分层/演义与正史"等约束，与本流程一致，照常执行；但**凡涉及史料引文与已核验事实，一律不动**。
4. 润色完成后，`待润色/<主题>.md` 即**终稿**。可再复制一份到 `过程稿/润色后-终稿.md`（可选），chmod 777。
5. **最终汇报**（此处才做）：向用户汇报——终稿路径、校验总轮数、校验修订摘要、保留的演绎项、需人工拍板的存疑项/未解决项、以及润色做了哪些文风改动；并说明 `过程稿/` 里保留了校验定稿（`润色前-校验定稿.md`）与润色终稿两份，便于对比回退。

## 注意事项

1. **不要跳过裁决直接把豆包报告全量喂给 revise**——会把演绎改没、且永不收敛。
2. 豆包回复解析失败（没按格式输出）时，不要猜：把原文回复交主会话人工解析归类。
3. API 调用失败：报错给用户决定是否重试，不静默吞掉。
4. 中文编码全程 UTF-8；文章传参一律经文件+python3，见④。
5. 每轮结束都要先落盘再进下一步，任何一步中断，磁盘上都有完整现场（当前版本+各轮报告），便于断点续跑：重跑时检测 `过程稿/` 已有产物，从最后一轮之后继续。
6. **润色必须在史实校验闭环收敛之后（⑥在⑤之后）**，且只做一次，润色后不再回②校验。断点续跑时若 `过程稿/润色前-校验定稿.md` 已存在、而最新一轮豆包报告为"未发现史实错误"，说明校验已定稿，直接从⑥润色继续。
7. **润色不得动史实与史料引文**：润色只改文风，凡人名/时间/官职/数字/因果/文言引文一律保留原样，避免把已核验的史实又改错（见⑥红线）。
